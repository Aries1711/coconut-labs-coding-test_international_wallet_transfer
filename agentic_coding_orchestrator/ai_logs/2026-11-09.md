# 2026-11-09 — build log

## Decisions

**Frankfurter v2 probed before planning.** `GET /v2/rate/USD/EUR` returned
`{"date":"2026-11-09","base":"USD","quote":"EUR","rate":0.89315}`, and USD/IDR
answered too. Worth the 3 seconds: the whole conversion feature hangs on that
endpoint existing in the shape the brief assumed, and the plan's rate handling
was written against a real response rather than a guess.

**Rate kept as a decimal string, not a number.** The client pulls the raw `rate`
token out of the response text with a regex instead of using `JSON.parse`'s
number. Owner's rule was "money is never a float"; a rate parsed to `number` and
then multiplied is the same class of mistake one level removed.

**Both legs of a transfer/conversion are one ledger entry.** Chosen over a
debit+credit pair so there is no state in which half a move exists. Atomicity
falls out of the data model instead of needing a transaction.

**Cache Components and Tailwind v4 both removed from the scaffold.** Decided to
change the toolchain rather than the owner's machine — see the two defects below.

## Defects found and fixed

**Pages 500ed while all 27 API checks passed.** Two independent causes, both from
`create-next-app`'s Next 16 defaults:

1. `nextConfig.cacheComponents: true` rejects `export const dynamic = "force-dynamic"`
   outright. Root cause: the scaffold opts into Cache Components, which is the
   wrong model for this app — every page reads an in-memory ledger per request
   and must never be prerendered. Fixed by dropping the flag, keeping `force-dynamic`.
2. `globals.css` failed to compile: Tailwind v4's compiler `require()`s
   `magic-string`, an ESM module, and `require(ESM)` is unflagged only from Node
   22.12; this machine has 22.2.0 and no other version installed. Fixed by
   pinning Tailwind 3.4 + PostCSS rather than installing a new Node on the
   owner's machine without asking.

The first acceptance run also hit a **stale process on port 3000**, so every
request was answered by an unrelated app (404s on routes that exist). The dev
server had logged "Port 3000 is in use … using 3001"; reading the server's own
output before trusting a test result would have saved a cycle.

**Funds re-checked after the rate `await`.** Found in the review pass, not by a
test: `convert` validated the balance, then awaited Frankfurter, then appended.
That `await` yields the event loop, so two concurrent conversions could both pass
the check and overdraw the source wallet. Now the balance is re-checked
immediately before the append. Still not a substitute for a real lock, and the
README says so.

**Wallet filter on `/transactions` reported as not working.** The filter was a
native `<form method="get">` whose only trigger was an explicit *Apply* click.
Server-side filtering was verified correct by URL before changing anything
(`?walletId=jpy-main` → 2 rows, `usd-main` → 5, `gbp-main` → 0, empty → all 12),
so the query handling was never at fault and was left alone. The interaction was
replaced: the select now navigates on change via the router, with the URL still
the source of truth so a filtered view stays shareable. The Apply button is gone,
since a two-step filter that looks like a one-step filter is the bug whether or
not the submit fires. Not reproduced in a browser — no browser automation was
available in the session — so the root cause is stated as the interaction, not a
specific browser behaviour.

**Three test expectations were wrong, not the code.** `Intl`/CLDR reports IDR with
**2** fraction digits, so IDR is held in sen. The brief names `Intl` as the source
of truth for decimals, so the implementation was correct and the assertions
(written from the assumption IDR has 0 decimals, like JPY) were corrected. Noted
as a limitation rather than special-cased, because overriding CLDR per currency
is the kind of hard-coded table that silently rots.

## Native select replaced with a custom listbox

Reported: opening the "Filter by wallet" dropdown showed the options panel
anchored far from the trigger (desktop, mobile and tablet), and on mobile the
option text was tiny.

Root cause, not a layout bug: that panel was the browser/OS's own native
`<select>` popup. Its position and font scale are rendered by the platform, not
by page CSS — there is no Tailwind class that reliably controls where a native
select opens or how large its text renders, and that varies by OS and browser.
No amount of positioning CSS on the trigger would have fixed it.

Fix: `WalletFilter` is now a hand-built listbox (button + `role="listbox"`
panel, Tailwind only, no component library) instead of a native `<select>`, so
position, width and type scale are fully ours and consistent across devices.
Kept: apply-on-select behaviour and the URL as the source of truth from the
previous fix, which were never the problem. Added: Escape to close, arrow-key
navigation, outside-pointerdown-to-close (covers touch, not just mouse).

Not verified in an actual mobile browser — no browser automation available in
this session — so this is confirmed by code review and server-rendered markup,
not a screenshot.
